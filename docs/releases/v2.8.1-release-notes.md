# UVHTTP v2.8.1 Release Notes

**Release Date**: 2026-09-29
**Version**: 2.8.1
**Type**: Patch Release (Performance Regression Fix & CI Gate Rewrite)

## Overview

UVHTTP v2.8.1 is a **patch release** that fixes a performance regression v2.8.0 introduced and rewrites the benchmark regression gate so it can actually detect such regressions.

v2.8.0's zero-copy writev path applied to **all** non-TLS responses. For small responses, splitting header and body into two iovecs is slower than the single-buffer copy path: on a core-pinned server with `wrk -t4 -c100`, the `/` endpoint measured **13.9% below v2.7.2**. The fix gates writev behind a body-size threshold, restoring `/` to 98.7% of v2.7.2 while leaving the `/large` zero-copy gain untouched (1.51x).

The regression escaped v2.8.0's gate because that gate compared absolute RPS against a hard-coded baseline, and the same commit drifts up to 40% between runs on shared runners. The gate is now a **same-runner paired comparison**: head and base are built in one job and measured alternately, and the pass/fail decision is a ratio between them rather than an absolute number.

## 🐛 Key Changes

### 1. 零拷贝 writev 增加 body 尺寸阈值 (PR #387)

**Problem**: v2.8.0 的 writev 对全部非 TLS 响应生效。小 body 时 header/body 双 iovec 比单缓冲拷贝路径更慢——`/` 比 v2.7.2 低 13.9%（同机配对实测，服务端绑核单核，`wrk -t4 -c100`）。

**Fix**:
- 仅当 `response->body_length >= UVHTTP_ZEROCOPY_MIN_BODY` 才走 writev，阈值默认 **4096 字节**，可经 CMake 调整（`cmake -DUVHTTP_ZEROCOPY_MIN_BODY=8192 ...`），头文件里保留 `#ifndef` 默认值以覆盖非 CMake 构建
- 阈值判断使用**压缩前**的 body 长度：gzip 命中路径仍走拷贝，语义与 TLS/非法 client 回退一致
- TLS 路径、非 TCP client、`response->client` 为空等场景继续回退拷贝路径，行为不变

**Result**:
- `/` 恢复到 v2.7.2 的 98.7%
- `/large` 零拷贝增益不变（1.51x，仍高于拷贝路径基线）
- 合入前由新的同机配对门禁实测（base = 含全量 writev 的 main）：`/` **+23.4%**、`/json` **+27.6%**、`/large` **+1.8%**，MAD 2–4%，10 轮配对中 0 轮低于限制

### 2. 基准回归门禁改为同机配对比较 (PR #388)

**Problem**: 原门禁拿绝对 RPS 与内置基线（83K/81K/8.8K）比较。共享 runner 上同一 commit 跨 run 的中位数漂移可达 40%，绝对阈值实际 gate 的是机器运气而不是代码——本次 `/` 回退 13.9% 就是这样漏掉的（同期绝对基线仍报 73–92% 通过）。

**New design**:
- 同一 runner、同一 job 内检出并构建 base（PR base sha / 上一个 release tag / 手动 `base_ref`），head 与 base 两台 `benchmark_unified` 分别监听 18081 / 18082
- 门禁端点按轮次交替测量，各 10 轮；奇数轮先压 head、偶数轮先压 base，抵消单次 run 内的热漂移
- `regression_check.py --compare` 按 round 配对取 head/base **比值中位数**，判定条件为中位数 < 90% **且**多数配对本身也低于 90%
- **fail-closed**：base 缺数据、有效配对 <3 轮、或被 gate 端点在任一 CSV 缺失，同样判失败——空跑的 gate 不算通过
- 门禁端点清单单一来源为 workflow 的 `GATE_ENDPOINTS`，经 `--gate` 传入脚本
- 绝对 RPS 基线降级为报告信息，不再参与判定

**为什么用「中位数 + 多数」而非置信下界**：比值噪声本身重尾——一个零 C 改动的 PR 上，10 轮配对仍给出中位数 97.4%、MAD 14.4%（单轮偏离中位数可达 −28% / +23%）。先试的稳健置信下界（中位数 − 1.7·MAD-SE）会把同一构建判红，改后的双条件在同一次对比的第三次运行给出 `/` 98.4%、仅 3/10 配对低于限制，PASS；而真实的 writev 小 body 回退（−14%、散布约 2%）几乎每个配对都在阈值以下，仍被 gate 捕获。

**顺带修掉的潜伏缺陷**：
- **token 权限**：仓库 `default_workflow_permissions = read`，benchmark job 的 PR 评论与趋势落库一直无法执行。写权限拆到独立 `trend` job，其余 job 显式声明权限（构建 PR head 代码的 job 不持有可写 `contents` token）
- **`wrk -L`**：原命令未开延迟分布选项，p99 解析拿到空值
- **artifact 嵌套**：`upload-artifact` 与 `/tmp` 路径混用会保留绝对路径，导致产物目录结构不可预期
- **`if: always()`**：产物上传与 PR 评论此前在 gate 失败时跳过，等于失败现场没有证据
- **label 依赖**：门禁按 `benchmark` label 触发，PR 未打 label 时静默跳过——审核清单增加「先看 label」一项

## 🔒 Compatibility

- **零破坏性变更**: patch release，API 完全向后兼容
- **构建新增选项**: CMake 变量 `UVHTTP_ZEROCOPY_MIN_BODY`（默认 4096）；不调大即为默认行为
- **行为变化**: body < 4096 字节的非 TLS 响应改回拷贝路径发送——仅影响吞吐，不影响 wire 上的字节序与响应内容
- **CI 行为变化**: 基准门禁改为配对比较，绝对基线不再 gate；`ci-benchmark.yml` 需 `benchmark` label 才会运行门禁
