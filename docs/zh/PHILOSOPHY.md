# UVHTTP 设计哲学

> 本文阐述 UVHTTP 的核心设计哲学：它**是什么**、**不是什么**、以及**为什么这样设计**。
> 所有决策和代码评审都以此为准绳。

---

## 1. 项目定位：一个组件，不是一个框架

UVHTTP 是一个 **HTTP/1.1 与 WebSocket 服务器 C 库**，不是应用服务器（nginx、Apache），也不是框架（Express、Flask）。

**定位的含义：**

| 项目是 | 项目不是 |
|---------|-----------|
| 一个可嵌入的 C 库 | 一个独立守护进程 |
| 一个协议处理组件 | 一个业务逻辑容器 |
| 应用的一部分 | 应用的全部 |

**推论：** UVHTTP 不提供认证、授权、数据库、模板引擎、会话管理、配置热加载。这些属于业务层。UVHTTP 只做一件事——正确处理 HTTP 与 WebSocket——并把它做好。

---

## 2. 分发模型：只发源码，用户自行编译

UVHTTP **不发布二进制**：没有 .deb 或 .rpm 包，也没有预编译静态库。用户这样获取：

```bash
git clone --recurse-submodules https://github.com/adam-ikari/uvhttp.git
cd uvhttp && mkdir build && cd build
cmake .. && make
```

### 这意味着什么

**1. 版本控制覆盖 API，不覆盖 ABI**

用户总是从源码编译，并与自己的应用静态链接，因此**ABI 兼容性不是承诺**。版本号（SemVer）承诺的是**源码级 API 兼容性**：

```
MAJOR.minor.patch
  │      │      └── 不破坏 API 的修复（bug 修复、测试、文档）
  │      └──────── 不破坏 API 的新功能（新函数、新模块）
  └─────────────── 破坏 API 的变更（签名变更、删除、行为不兼容）
```

- **PATCH 发布**：完全向后兼容，用户代码无需改动
- **MINOR 发布**：向后兼容，新功能可选，现有代码继续可用
- **MAJOR 发布**：API 不兼容，用户必须修改代码

**2. 编译时裁剪是核心特性**

用户通过 CMake 选项选择所需功能：
```cmake
cmake .. -DBUILD_WITH_WEBSOCKET=OFF -DBUILD_WITH_COMPRESSION=OFF
```

未使用的功能不参与编译，不增加代码体积。这是嵌入式优先的落地方式。

**3. 依赖管理归用户**

UVHTTP 用 git submodule 管理依赖（libuv、llhttp、mbedtls、xxhash、miniz）。一次 `--recurse-submodules` 克隆即可取齐全部依赖。这符合"零外部依赖"哲学：任何依赖都不来自系统包管理器。

## 3. 嵌入式优先

UVHTTP 优化的是**嵌入式设备与长时间运行的服务**，不是峰值吞吐量。

### 优先级

```
内存安全 > 内存稳定性 > 二进制体积 > 启动时间 > 峰值吞吐量
```

### 指标

| 指标 | 目标 | 衡量方式 |
|------|------|---------|
| 内存泄漏 | 0（经 ASan 证明） | 每次发布的 ASan 门禁 |
| 长时间运行 RSS | 不增长 | `scripts/performance/long_run_memory.sh` |
| 静态库体积 | 约 257 KB | Release 构建，stripped |
| 32-bit 支持 | 必需 | 手工 `-m32` 构建；无 CI 任务 |
| 冷启动 | 约 310 ms | 进程启动到首字节 |
| 编译时裁剪 | 按需付费 | CMake 特性开关 |

### 低资源使用优先

UVHTTP 的"嵌入式优先"覆盖**所有资源**，不只是**内存**。在资源受限设备上，CPU、内存、带宽、电池都有成本：

| 资源 | UVHTTP 的做法 | 体现 |
|------|--------------|---------|
| **内存（RAM）** | 最小静态占用 + 零泄漏 | 编译时裁剪、无全局变量、缓存行对齐 |
| **CPU** | 零成本抽象、无中间层 | 直接调用 libuv、编译期宏消除 |
| **带宽** | 零拷贝路径 | 原生 sendfile，无多余缓冲区拷贝 |
| **存储** | 小静态库 | 约 257 KB 的 stripped 静态库 |
| **启动** | 快速冷启动 | 约 310 ms 到首字节 |

**核心信念：在低资源场景下，每个字节、每个 CPU 周期都是可度量的成本。**

UVHTTP 的每个选择都遵循这一信念：

- **编译时裁剪**：未使用的功能不编译，不占 ROM 或 RAM。
- **无全局变量**：状态放在实例内，因此支持多实例，销毁即可释放一切。
- **零拷贝**：sendfile 把大文件送入 socket，不经过用户态缓冲区。
- **单一分配器钩子**：嵌入式用户注入自己的内存池，掌控每一次分配。
- **32-bit 支持**：指针减半，结构体随之缩小。

> 反之，让代码更复杂、更大或依赖更多的"优化"，即使能略微提升峰值吞吐量，也违背低资源优先——除非实测数据表明总资源占用下降。

### 由此得出

- **峰值吞吐量不是卖点**（nginx 和 h2o 更强）。
- **每个连接泄漏 1 KB 就是 bug。** 在嵌入式设备上，10 小时内就会耗尽内存。
- **32-bit 支持不是可选项。** 许多嵌入式设备仍是 32-bit。
- **编译时裁剪**意味着用户只链接所需功能，不浪费字节。

## 4. 内存安全是基础设施

内存安全不是 UVHTTP 的一个特性，而是**基础设施，与编译器同等重要**。

### 三层

| 层 | 机制 | 频率 |
|------|------|------|
| **编译期** | 构建矩阵、cppcheck、测试有效性检查 | 每个 PR |
| **发布** | 在已测矩阵上跑快速测试，ASan 门禁 | 每次发布 |
| **每夜** | UBSan 测试、覆盖率、压力测试、长时间运行 RSS 检查 | 每夜 CI |

### 原则

- **ASan/UBSan 零发现是发布门禁**，不是可选目标。
- **不允许 `no_sanitize("address")`。** 禁用 sanitizer 是最后手段，且需要解释和跟踪 issue。
- **Valgrind 有辅助作用，但不能替代 ASan。** ASan 捕获更多 bug，运行更快。
- **内存泄漏是功能 bug**，与逻辑错误同级。

## 5. 测试是基础设施

UVHTTP 的测试代码（52K 行）是生产代码（21K 行）的 **2.5 倍**。这不是过度工程，而是**基础设施**。

### 测试哲学

| 生产代码 | 测试代码 |
|---------|---------|
| 21K 行 C | 52K 行 C++（gtest） |
| 47 个文件 | 128 个文件 |
| 实现行为 | 证明行为正确 |

### 原则

- **测试不是附属品。** 测试代码与生产代码同级。
- **测试门禁。** 全部测试通过才发布；PR CI 运行编译、cppcheck、测试有效性、文档同步和构建矩阵。
- **测试分离。** 生产代码不含测试代码（无 `#ifdef TEST`）。
- **覆盖率不是目标，正确性才是。** 高覆盖率是值得拥有的副产品。
- **新功能附带测试。** 没有测试的功能不存在。

## 6. 零成本抽象

零成本抽象是 UVHTTP 的核心工程原则：**抽象在运行时零成本，只是编译期的组织手段**。这一思路来自 C++ 的 zero-overhead principle，用 C 实现：预处理宏和静态内联函数在代码生成前消除抽象。

### 为什么是核心

UVHTTP 面向嵌入式和低资源场景（第 3 节）。为了写得方便而引入的抽象，若让每个请求多付出几个分支、一次间接调用或一层栈帧，就会侵蚀吞吐量、增加指令缓存压力并增大二进制体积。因此：

> **允许抽象，但抽象必须零成本。否则它不是抽象，而是负债。**

### 三种零成本手段

| 手段 | 原理 | 示例 |
|------|------|------|
| **编译期宏** | 特性开关在预处理阶段移除未使用代码 | `UVHTTP_FEATURE_*` 开关、`UVHTTP_LIKELY/UNLIKELY` 分支预测 |
| **静态内联函数** | `static inline` 在优化构建中内联，无调用开销 | `uvhttp_hash`、`uvhttp_method_to_string` 快速路径 |
| **直接调用，无中间层** | 直接调用 libuv / llhttp / mbedtls，不包装转发 | 直接使用 `uv_tcp_*`、`llhttp_execute` |

### 验证

零成本抽象需要**证据**，不是声明：

- **反汇编检查**：热路径不含抽象层的残留调用。
- **基准对比**：启用或禁用某个抽象，吞吐量无差别（见 `docs/PERFORMANCE_TARGETS.md`）。
- **代码审查**：编译器必须能完全消除性能关键路径上的抽象。

### 与低资源优先的关系

零成本抽象是**手段**，低资源优先是**目的**：

- 零成本抽象 → CPU 与指令缓存效率
- 低资源优先 → 内存、体积与启动时间的综合视角

## 7. 代码设计规则

### 无全局变量

所有状态通过 libuv 的 `data` 指针（`loop->data`、`handle->data`）传递。这使 UVHTTP 支持：
- 多实例（同一进程内多个服务器）
- 单元测试（无全局状态污染）
- 可测试性（所有状态可注入）

### 统一错误系统

所有可能失败的函数返回 `uvhttp_error_t`——一种携带错误码、描述和恢复提示的错误类型。错误信号不用 `-1`、`NULL` 或 `errno`。

### 缓存行对齐

热路径结构体（`uvhttp_request_t`、`uvhttp_response_t`、`uvhttp_connection_t`）显式按缓存行（64 字节）对齐并填充。这不是微优化，而是对多核伪共享的防御。

### 编译期特性开关

每个可选特性都由编译期宏控制（`UVHTTP_FEATURE_COMPRESSION`、`UVHTTP_FEATURE_WEBSOCKET` 等）。关闭的特性在预处理阶段消失，运行时零成本。

## 8. C 标准：C11

UVHTTP 用 C11 构建，不是 C99：`CMakeLists.txt` 设置 `CMAKE_C_STANDARD 11`。代码依赖 `_Static_assert` 等 C99 没有的 C11 设施。

**选用：**
- 可移植性：GCC 4.8+ 和 Clang 3.3+ 支持代码用到的 C11 特性。
- 嵌入式工具链：这一领域的交叉编译器支持 C11。
- 最小惊异：C11 行为是已知的。

**未使用：**
- C11/C17 的可选特性（匿名结构体、泛型表达式）：提高编译器要求，收益很小。
- C23 特性：多数嵌入式编译器尚不支持。

## 9. 项目边界：不做的事

UVHTTP 有意不做以下事情。若你的场景需要它们，UVHTTP 可能不适合。

| 领域 | 原因 |
|------|------|
| **HTTP/2** | HTTP/2 的多路复用与 libuv 事件模型冲突；它需要应用可见的多路复用，而非透明连接复用。 |
| **HTTP/3** | 基于 QUIC，需要不同的传输层，超出轻量级 C 库的范围。 |
| **Windows 原生支持** | libuv 可在 Windows 运行，但 UVHTTP 的零拷贝路径（sendfile）和对 epoll 的深度依赖会让 Windows 支持成为大量工作。 |
| **异步 DNS** | libuv 内置 DNS 解析，但 UVHTTP 是服务器库，不承担客户端角色。 |
| **自动重连与健康检查** | 这些是业务层关注点，不是协议层关注点。 |
| **配置热加载** | 嵌入式场景很少需要；需要它的应用可在应用层实现。 |
| **插件系统** | 动态加载与嵌入式安全目标冲突；用户在编译时链接扩展功能。 |

> 这些边界不是永久的。若社区贡献能在不违背核心哲学的前提下使某项成为可能，项目可以重新评估。

## 10. 嵌入验证：真实使用是唯一有效的测试

三层门禁（编译、测试、CI）守护 UVHTTP 的代码质量，但三层都在**库内部**验证。把 uvhttp 嵌入 qwrt 暴露了 6 类问题。它们全部通过了 uvhttp 自己的测试套件，却在真实嵌入中集中失败。

**教训：测试通过不等于嵌入者能用。**

### 原则

1. **嵌入验证就是测试。** 每个新功能、API 或模块发布前，必须至少由一个真实嵌入者验证通过。
2. **没有嵌入验证的代码视为未验证**，即使内部测试通过。
3. **嵌入清单是基础设施。** 每次重要发布前，用清单验证所有已知嵌入维度。

### qwrt 嵌入暴露的问题

| 类别 | 问题 | 根因 |
|------|------|------|
| **枚举对齐** | llhttp 与 uvhttp 的方法枚举不对齐；强转损坏 POST/PUT/DELETE | 枚举值耦合未文档化，且无编译期断言 |
| **标准兼容** | gzip 输出使用 zlib 包装（0x78），而非标准 gzip（0x1f8b） | 测试只检查解压，未用标准解码器 |
| **路径规范化** | index 文件路径无前导斜杠 → 403 | 路径校验与路径生成不一致 |
| **协议合规** | HTTP 头匹配区分大小写，拒绝合法的大小写变体 | 测试客户端使用规范大小写，掩盖了问题 |
| **处理管线** | 路由未命中时没有兜底 handler，嵌入者无法拦截 | 设计未考虑嵌入者需要最后一道防线 |
| **静态全局** | gzip 缓存使用模块级静态全局变量 | 违反无全局变量规则；CI 未发现 |

每次嵌入都验证这些类别。

### 对本文的补充

前八章定义 UVHTTP 的**设计哲学**（做什么、不做什么、为什么）。本章定义**验证哲学**（如何证明做对了）。

UVHTTP 的验证栈：

```
┌─────────────────────────────────────┐
│ 第三层：嵌入验证                     │ ← 本章定义
├─────────────────────────────────────┤
│ 第二层：构建配置矩阵                 │ ← 已覆盖（build-matrix）
├─────────────────────────────────────┤
│ 第一层：测试 + ASan/UBSan（基础）    │ ← 已完备
└─────────────────────────────────────┘
```

第一层已完备。第二层由 ci-pr.yml 中的 build-matrix 任务覆盖，验证全开、最简、ROUTER_CACHE、静态文件和无压缩等构建。第三层通过嵌入清单落实。本章连接第一层与第三层。
